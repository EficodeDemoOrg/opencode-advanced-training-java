Atlas Inventory
===
# Introduction
Atlas Inventory is a small and simple hardware inventory application. Its purpose is solely to serve as sample code for training purposes, for a course on agentic training with OpenCode. It provides a browser interface and an HTTP API for viewing, adding, updating, and removing component records.

The application uses a deliberately compact technology stack:
- Java 17-compatible source and bytecode
- JDK `HttpServer`
- SQLite through JDBC
- Vanilla HTML, CSS, and JavaScript
- Maven and JUnit 5

No application framework, ORM, or frontend build tool is required.

# Workshop Exercises
This repository is the project folder for an agentic-coding workshop run with [opencode](https://opencode.ai). The exercises live in [`exercises/`](exercises/README.md) — start there. 

Notes for trainers are also found there: [`exercises/TRAINER-NOTES.md`](exercises/TRAINER-NOTES.md).

# Prerequisites
In order to run the exercises, participants need to have access to: 
- JDK 17 or later
- Maven 3.9 or later

To check the installed versions:

Bash and PowerShell:
```bash
java -version
mvn -version
```

# Build and Test
Run all automated tests and build the executable JAR:

Bash and PowerShell:
```bash
mvn clean verify
```

The build creates the self-contained application at:

```text
target/inventory-app.jar
```

# Run
Start the packaged application:

Bash and PowerShell:
```bash
java -jar target/inventory-app.jar
```

Open [http://localhost:8080](http://localhost:8080) in a browser. Stop the application with `Ctrl+C`.

The server listens only on the local loopback interface. It cannot be reached from another computer without a code or configuration change. 

## Configuration
The application reads these optional environment variables:

| Variable       | Default             | Description                           |
|----------------|---------------------|---------------------------------------|
| `PORT`         | `8080`              | Local HTTP port, from 1 through 65535 |
| `INVENTORY_DB` | `data/inventory.db` | Path to the SQLite database file      |

Bash:
```bash
PORT=8090 INVENTORY_DB=data/workshop.db java -jar target/inventory-app.jar
```

PowerShell:
```powershell
$env:PORT = "8090"
$env:INVENTORY_DB = "data/workshop.db"
java -jar target/inventory-app.jar
```

The Bash form sets both variables for that one command only. The PowerShell form sets them for the rest of the session, so later runs in the same window keep using port 8090. When done, open a new window, or clear the variables with `Remove-Item Env:PORT, Env:INVENTORY_DB`, to go back to the defaults.

# Database
The application creates its own database and its parent directory at startup. When the inventory table is empty, it inserts a small fictional data set of electronic components.

It is easy to reset the default database:
1. Stop the application.
2. Delete `data/inventory.db`.
3. Start the application again.

The database will be recreated and seeded. Do not delete the database while the application is running.

# Inventory Data
Each inventory item contains:

| Field             | Type         | Rules                             |
|-------------------|--------------|-----------------------------------|
| `id`              | Number       | Generated by the database         |
| `partNumber`      | Text         | Required, unique, <=50 characters |
| `name`            | Text         | Required, <=100 characters        |
| `category`        | Text         | Required, <=50 characters         |
| `storageLocation` | Text         | Required, <=50 characters         |
| `quantity`        | Whole number | Required, non-negative [^1]       |
| `reorderLevel`    | Whole number | Required, non-negative            |
| `description`     | Text         | Optional, <=500 characters        |
---
[^1]: The non-negative check is applied when an item is created. The update path does not currently re-check it, so `PUT` can store a negative quantity. This deliberate gap is used by the workshop exercises.

# HTTP API
The API uses JSON responses. Create and update requests use `application/x-www-form-urlencoded` bodies, the same format submitted by a standard HTML form.

| Method   | Path              | Success | Description                           |
|----------|-------------------|--------:|---------------------------------------|
| `GET`    | `/api/items`      |   `200` | List all items                        |
| `GET`    | `/api/items/{id}` |   `200` | Get one item                          |
| `POST`   | `/api/items`      |   `201` | Create an item                        |
| `PUT`    | `/api/items/{id}` |   `200` | Replace an item                       |
| `DELETE` | `/api/items/{id}` |   `204` | Delete an item                        |
| `GET`    | `/health`         |   `200` | Check application and database health |
---

## Example Response
```json
{
  "id": 1,
  "partNumber": "PCB-CTRL-100",
  "name": "Control Board",
  "category": "Circuit Board",
  "storageLocation": "A-01-01",
  "quantity": 12,
  "reorderLevel": 4,
  "description": "General-purpose controller board"
}
```

## Create an Item
Bash, using `curl`:
```bash
curl -X POST http://localhost:8080/api/items \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "partNumber=RES-10K" \
  --data-urlencode "name=10 kOhm Resistor" \
  --data-urlencode "category=Resistor" \
  --data-urlencode "storageLocation=C-08-01" \
  --data-urlencode "quantity=100" \
  --data-urlencode "reorderLevel=25" \
  --data-urlencode "description=Quarter-watt axial resistor"
```

PowerShell, using `Invoke-RestMethod`:
```powershell
$body = @{
    partNumber      = "RES-10K"
    name            = "10 kOhm Resistor"
    category        = "Resistor"
    storageLocation = "C-08-01"
    quantity        = 100
    reorderLevel    = 25
    description     = "Quarter-watt axial resistor"
}

Invoke-RestMethod -Method Post -Uri "http://localhost:8080/api/items" `
  -ContentType "application/x-www-form-urlencoded" -Body $body
```

## Update an Item
Replace `{id}` with an existing numeric item identifier.

Bash:
```bash
curl -X PUT http://localhost:8080/api/items/{id} \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "partNumber=RES-10K" \
  --data-urlencode "name=10 kOhm Resistor" \
  --data-urlencode "category=Resistor" \
  --data-urlencode "storageLocation=C-08-02" \
  --data-urlencode "quantity=80" \
  --data-urlencode "reorderLevel=25" \
  --data-urlencode "description=Quarter-watt axial resistor"
```

PowerShell:
```powershell
$body = @{
    partNumber      = "RES-10K"
    name            = "10 kOhm Resistor"
    category        = "Resistor"
    storageLocation = "C-08-02"
    quantity        = 80
    reorderLevel    = 25
    description     = "Quarter-watt axial resistor"
}

Invoke-RestMethod -Method Put -Uri "http://localhost:8080/api/items/{id}" `
  -ContentType "application/x-www-form-urlencoded" -Body $body
```

`PUT` replaces the whole record, so send every field, any value you leave out is treated as missing, not as unchanged.

## Delete an Item
Bash:
```bash
curl -X DELETE http://localhost:8080/api/items/{id}
```

PowerShell:
```powershell
Invoke-RestMethod -Method Delete -Uri "http://localhost:8080/api/items/{id}"
```

## Errors
Errors use a consistent JSON response:

```json
{"error":"Name is required"}
```

`curl` prints that body as-is. PowerShell's `Invoke-RestMethod` instead raises a
terminating error on any 4xx or 5xx response and prints nothing, so read the
body from the exception:

```powershell
try {
    Invoke-RestMethod -Method Post -Uri "http://localhost:8080/api/items" `
      -ContentType "application/x-www-form-urlencoded" -Body $body
} catch {
    $_.Exception.Response.StatusCode.value__
    $_.ErrorDetails.Message
}
```

Common status codes are:

| Status | Meaning                                     |
|-------:|---------------------------------------------|
|  `400` | Invalid input or malformed identifier       |
|  `404` | Item or resource not found                  |
|  `405` | HTTP method not supported for the path      |
|  `409` | Part number already exists                  |
|  `500` | Unexpected server or database failure       |
|  `503` | Health check could not access the database  |
